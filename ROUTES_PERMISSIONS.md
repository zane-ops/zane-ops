# Routes & Permissions

Generated by introspecting the Django URL resolver (`ENABLE_EE=true`) and reading `frontend/app/routes.ts` + role guards.

## Role model

`WorkspaceRole` is an ordered integer scale — every permission check is `role >= X`, so higher roles inherit everything below.

| Role | Value | Backend permission | Frontend name |
| --- | --- | --- | --- |
| Guest | 10 | `IsWorkspaceGuest` | `Guest` |
| Member | 30 | `IsWorkspaceMember` | `Member` |
| Admin | 40 | `IsWorkspaceAdmin` | `Admin` |
| Owner | 50 | `IsWorkspaceOwner` | `Owner` |
| Instance superuser | — | `IsInstanceOwner` (`user.is_superuser`) | `ServerAdmin` |

Other backend permissions:

- `HasWorkspace` — resolves the active workspace from the session; paired with every workspace-role check.
- `InternalZaneAppPermission` — Basic auth with `zaneops:$SECRET_KEY`, for internal agents (fluentd).
- `AllowAny` / `IsAuthenticated` — DRF built-ins.

DRF default (`settings.REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES`) is `[HasWorkspace, IsWorkspaceGuest]`.

Guest access is additionally narrowed by `get_accessible_projects()`: a Guest only sees projects explicitly listed in `membership.accessible_projects`, while Member and above see every project in the workspace.

# Frontend (React Router)

Role gating uses two helpers in [app/lib/utils.ts:617](frontend/app/lib/utils.ts#L617) and [app/lib/queries.ts:99](frontend/app/lib/queries.ts#L99):

- `hasMinRole(user, roleName)` — render-time check for hiding UI.
- `ensureMinRole(queryClient, roleName)` — `clientLoader` guard that throws a 404 when the role is insufficient.

Most routes are **not** guarded in the loader; they inherit the workspace layout and rely on the API returning 403. The table below marks what is actually enforced client-side.
