# Routes & Permissions

Generated by introspecting the Django URL resolver (`ENABLE_EE=true`).

> The frontend route/permission section was removed pending an update — this covers the backend only.

## Role model

`WorkspaceRole` is an ordered integer scale — every permission check is `role >= X`, so higher roles inherit everything below.

| Role | Value | Backend permission | Frontend name |
| --- | --- | --- | --- |
| Viewer | 10 | `IsWorkspaceViewer` | `Viewer` |
| Member | 30 | `IsWorkspaceMember` | `Member` |
| Admin | 40 | `IsWorkspaceAdmin` | `Admin` |
| Owner | 50 | `IsWorkspaceOwner` | `Owner` |
| Instance superuser | — | `IsInstanceOwner` (`user.is_superuser`) | `ServerAdmin` |

Other backend permissions:

- `HasWorkspace` — resolves the active workspace from the session; paired with every workspace-role check.
- `InternalZaneAppPermission` — Basic auth with `zaneops:$SECRET_KEY`, for internal agents (fluentd).
- `AllowAny` / `IsAuthenticated` — DRF built-ins.

DRF default (`settings.REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES`) is **`[HasWorkspace, IsWorkspaceMember]`**. Viewer-reachable routes must opt in explicitly with `permission_classes = [HasWorkspace, IsWorkspaceViewer]` (or via `get_permissions()`); there are only 4 of them today.

Only these routes actually fall through to the default rather than declaring a permission themselves:

| Route | View |
| --- | --- |
| `/api/http-logs/fields` | `HttpLogsFieldsAPIView` |
| `/api/projects/{slug}/{env_slug}/service-list` | `ProjectServiceListAPIView` |

The other views without a `permission_classes` attribute (`ProjectsListAPIView`, `ProjectDetailsAPIView`, `ServiceDetailsAPIView`, `EnvironmentDetailsAPIView`, `SharedEnvVariablesViewSet`, `SharedRegistryCredentialsDetailsAPIView`, `WorkspaceDetailAPIView`) resolve their roles in `get_permissions()` — see the method-dependent table below.

Viewer access is additionally narrowed by `get_accessible_projects()`: a Viewer only sees projects explicitly listed in `membership.accessible_projects`, while Member and above see every project in the workspace.

## Gaps worth a look

1. **Viewer can currently reach almost nothing.** After the default flipped to `IsWorkspaceMember`, only `/api/settings`, `/api/workspaces/switch`, `/api/workspace/leave` and `GET /api/workspace` remain Viewer-reachable. Routes that used to serve Viewers (`/api/projects` GET, `/api/projects/{slug}` GET, `service-details` GET, `service-list`, `search-resources`, `detected-ports`, `http-logs/fields`) are now Member-only, pending the dedicated Viewer endpoints.
2. **`TriggerPreviewEnvironmentAPIView` assigns `permission_classes` twice** ([environments.py:671](../zane_api/views/environments.py#L671) then [environments.py:674](../zane_api/views/environments.py#L674)) — `AllowAny` is shadowed, so the effective role is Member even though the route is token-shaped (`/api/trigger-preview/{deploy_token}`) and carries a `deploy_webhook` throttle. Likely unintended.
3. **`ServiceDetailsAPIView.get_permissions()` returns `Member` on both branches** ([docker_services.py:1167](../zane_api/views/docker_services.py#L1167)) — dead override.
4. **No frontend for `/api/console/*`.** The instance user/workspace management endpoints (12 routes) have no counterpart in `frontend/app/routes.ts`.
5. **Commented-out permission classes** at [deployments.py:131](../zane_api/views/deployments.py#L131), [stacks.py:770](../compose/views/stacks.py#L770) and [container_terminal_consumer.py:55](../webshell/consumers/container_terminal_consumer.py#L55) — worth confirming those are deliberate.
